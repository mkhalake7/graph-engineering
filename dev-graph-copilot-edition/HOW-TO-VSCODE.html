Using Dev-Graph with GitHub Copilot Chat in VS Code

Install four custom chat modes and four prompts, then run the recommendation-backend workflow entirely from the Copilot Chat panel. No API keys required.

01Prerequisites

  • VS Code — recent version (1.90+, ideally the latest stable). Custom chat modes and prompt files are relatively new features.
  • GitHub Copilot Chat extension — installed and signed in. Verify the Copilot icon appears in your activity bar.
  • Copilot subscription with model access — Business/Enterprise plans typically expose Claude Sonnet/Opus and GPT-5 in the model picker.
  • Your recommendation-backend repo — checked out locally, and you're allowed to add a .github/ folder to it (or a personal fork if not).
  • The Copilot-edition bundle — dev-graph-copilot-edition.bundle (or an unpacked copy of the kit).
Feature availability. Custom chat modes (.chatmode.md) and prompt files (.prompt.md) are documented Copilot features but their UI location and enablement flags evolve. If a step below doesn't match your VS Code, check the Chat: Prompt Files and Chat: Mode Files Locations settings — you may need to explicitly point Copilot at .github/chatmodes/ and .github/prompts/.

02Install into your repo

The kit is designed to live inside your target repo so Copilot picks it up automatically for that workspace.

Easiest — use the installer script

# From inside the unpacked kit
python scripts/install-into-repo.py --target /path/to/your/recommendation-backend

# Preview first without writing
python scripts/install-into-repo.py --target /path/to/your/repo --dry-run

# Overwrite existing files (use with care — copilot-instructions.md is often team-owned)
python scripts/install-into-repo.py --target /path/to/your/repo --force

The installer copies .github/copilot-instructions.md, all chatmode and prompt files, and WORKFLOW.md. It refuses to clobber an existing copilot-instructions.md without --force, and skips individual chatmode/prompt files that already exist. Pure stdlib, no dependencies.

After installing, you can validate the result:

python scripts/validate-chatmodes.py --dir /path/to/your/repo/.github

Manual alternative — if you already have the git bundle

# 1. Unpack the bundle to a scratch location
mkdir ~/tmp/copilot-kit && cd ~/tmp/copilot-kit
git clone /path/to/dev-graph-copilot-edition.bundle .

# 2. Copy the .github/ folder and workflow doc into your repo
cd /path/to/your/recommendation-backend-repo
cp -R ~/tmp/copilot-kit/.github .
cp ~/tmp/copilot-kit/WORKFLOW.md .
cp -R ~/tmp/copilot-kit/examples .

# 3. Commit onto a branch and share with the team
git checkout -b devgraph/install-copilot-modes
git add .github/ WORKFLOW.md examples/
git commit -m "devgraph: add Copilot chat modes and prompts"
git push -u origin devgraph/install-copilot-modes

If you already have a .github/ folder

Merge, don't overwrite. The subfolders (chatmodes/, prompts/) and copilot-instructions.md should not conflict with typical repo contents, but check first.

ls .github/                     # see what's already there
cp -R ~/tmp/copilot-kit/.github/chatmodes .github/
cp -R ~/tmp/copilot-kit/.github/prompts .github/

# If copilot-instructions.md already exists, merge manually.
diff ~/tmp/copilot-kit/.github/copilot-instructions.md .github/copilot-instructions.md
Alternate placement. If your team prefers not to check these into the repo, place the files under .vscode/chatmodes/ and .vscode/prompts/ instead (workspace-scoped, not repo-scoped). Update chat.modeFilesLocations and chat.promptFilesLocations in .vscode/settings.json to point there.

03Reload VS Code & verify

Step 3.1
Reload the window

Press Cmd+Shift+P (or Ctrl+Shift+P on Windows/Linux) → type Developer: Reload Window → Enter.

Step 3.2
Open Copilot Chat

Press Ctrl+Cmd+I to open the chat panel, or click the Copilot icon in the activity bar and pick Chat.

Step 3.3
Verify the four chat modes

At the top of the chat panel, click the mode picker (usually shows "Ask", "Edit", "Agent"). You should now also see:

Mode picker ▾
├── Ask                       (built-in)
├── Edit                      (built-in)
├── Agent                     (built-in)
├── Spec Architect            ← from .github/chatmodes/
├── Coder                     ← from .github/chatmodes/
├── Grader                    ← from .github/chatmodes/
└── LLM Prompt Engineer       ← from .github/chatmodes/
Step 3.4
Verify the four prompts

In the chat input box, type /. A dropdown should appear with the built-in Copilot slash commands plus the custom prompts:

/                              (start typing to filter)
├── /explain                  (built-in)
├── /fix                      (built-in)
├── /new-task                 ← from .github/prompts/
├── /review-spec              ← from .github/prompts/
├── /coder-input              ← from .github/prompts/
└── /pr-body                  ← from .github/prompts/

If they don't appear, jump to Troubleshooting.

Step 3.5
Verify always-on instructions

Open a fresh chat in Ask mode. Type: What are the two runtime paths of this backend?

Copilot should describe the write-path enrichment pipeline (Glue → S3 → enrichment worker → OpenSearch) and the read-path /recommend API. That confirms .github/copilot-instructions.md is being auto-loaded.

04Pick a model per mode

Every mode has an independent model picker. Set each once and Copilot remembers your choice.

ModeRecommended model classWhy
Spec Architect Strong reasoning
Claude Opus 4.x · GPT-5		 Producing testable acceptance criteria requires judgment. A weaker model produces vague ACs.
Coder Capable coding
Claude Sonnet 4.x · GPT-5		 You want fast, high-throughput edits. Sonnet-class models are the sweet spot for iterative file editing in Agent mode.
Grader Strong reasoning
Claude Opus 4.x · GPT-5		 Independent verification benefits from the strongest model available. Do not use the same model as the Coder if you can help it — cross-model verification catches more.
LLM Prompt Engineer Strong reasoning
Claude Opus 4.x · GPT-5		 Prompt tweaks look tiny but have large downstream effects. Use the strongest model to evaluate wording changes.
To set the model: switch to the mode, click the model picker (next to the mode picker at the top of the chat panel), select your model. That's it — no config file to edit.

05The four chat modes

Each mode is a saved system prompt with a specific tool allowlist. Switching modes is like switching specialists.

Spec Architect
Read-only · JSON output

Turns a fuzzy task into a testable JSON spec with acceptance criteria, affected components, and a risk level. Cannot edit files. Refuses to invent requirements — asks clarifying questions when needed.

Coder
Agent mode · Edits + commands

Implements an approved spec by reading files, proposing edits, and running commands. Enforces minimum-change discipline. Stops when done and summarizes which AC each edit addresses.

Grader
Read-only · JSON verdict

Verifies a diff against the approved spec. Returns pass/fail per AC with actionable feedback. Independence rule: use a different model than the Coder, and open a fresh chat (no context bleed).

LLM Prompt Engineer
Prompt files only

Owns the enrichment and reranker prompts. Can edit files under prompts/ but not application code. Refuses to ship prompt changes without an eval-suite delta.

06The four prompts

Prompts are reusable inputs. Invoke by typing /name in the chat input. Each prompt is bound to the mode it makes sense in — invoking /new-task auto-switches you to Spec Architect mode.

/new-task
→ Spec Architect

Kicks off a new engineering task. Prompts you for the task text and any repo context, then produces a JSON spec.

/review-spec
→ Ask

Human gate helper. Walks you through a 7-item spec review checklist and gives an APPROVE / REJECT / APPROVE-WITH-EDITS recommendation.

/coder-input
→ Coder

Hands off an approved spec to the Coder mode with the right framing. Coder then iterates in Agent mode.

/pr-body
→ Ask

Assembles a well-formatted PR body from your trace log. Enforces the same section layout every time so PRs are scannable.

07Run your first task, click by click

The suggested first task: something tiny and reversible so you can shake out any UI issues without stakes. Example: "Add a one-line docstring to the top of the enrichment worker's main function."

Step 7.1 · Prep
Create a fresh branch and trace log
git checkout -b devgraph/hello-world
mkdir -p .dev-graph/tasks
echo "# Task: add docstring to enrichment worker main" > .dev-graph/tasks/hello-world.md

The .dev-graph/ folder is git-ignored (see the kit's .gitignore). This is your trace log — every step below appends to it.

Step 7.2 · Repo exploration (Ask mode)
Find the file

In the chat panel, switch to Ask mode. Type:

@workspace where is the enrichment worker's main function? Just show the file path.

Copilot returns something like workers/enrichment_worker.py. Add that to your trace log under ## Repo context.

Step 7.3 · Produce the spec
Spec Architect + /new-task

Switch to Spec Architect mode. In the chat input, type /new-task. When prompted:

  • task: "Add a one-line docstring to the top of the enrichment worker's main function."
  • context: paste the file path from Step 7.2
  • feedback: (leave empty)

Copilot returns a JSON spec. Copy the whole block into your trace log under ## Spec (proposed).

Step 7.4 · Human gate
/review-spec

In the same chat panel, type /review-spec and paste the JSON spec when prompted. Copilot runs the checklist. For a trivial task the recommendation should be APPROVE — for anything real it may be APPROVE-WITH-EDITS.

Copy the final approved spec into ## Spec (approved) in your trace log.

Step 7.5 · Code it
Coder + /coder-input

Switch to Coder mode. Type /coder-input and paste the approved spec. Copilot goes into Agent mode: proposes an edit to workers/enrichment_worker.py. Accept the hunk.

Step 7.6 · Verify locally
Run tests + lint
pytest -x -q
ruff check workers/

Paste the results into your trace log under ## Verification.

Step 7.7 · Grade it
Grader (in a new chat)

Open a new chat panel (don't reuse the Coder's chat — it will bias the Grader). Switch to Grader mode. Paste:

  • The approved spec (JSON)
  • Your diff — run git diff HEAD and paste, or use #file:workers/enrichment_worker.py
  • Your test output

Copilot returns a JSON verdict. If pass, copy into ## Grader (verdict). If fail, go back to Coder mode with the feedback.

Step 7.8 · Write the PR
/pr-body

Type /pr-body (any mode is fine — Ask is enough) and paste the full trace log. Copilot generates a clean PR body.

Step 7.9 · Ship it
Commit, push, open PR
git add -A
git commit -m "devgraph: add docstring to enrichment worker main"
git push -u origin devgraph/hello-world
gh pr create --title "..." --body "$(cat /tmp/pr-body.md)"

Or use the VS Code Source Control panel and the GitHub Pull Requests extension — paste the generated body into the PR description field.

You just ran the full graph by hand. That's the point of the Copilot edition — the same structure as the automated kit, executed manually. The bigger the task, the more the discipline pays off.

08Adaptive behavior: reading the codebase & adjusting

Every mode is instructed to read before writing and to pause when reality contradicts the plan. This is what turns the kit from a rigid checklist into a system that respects your codebase.

What each mode adapts

ModeWhat it readsHow it adapts
Spec Architect Existing similar features, current field shapes, test fixtures, migration patterns Mirrors prior art in AC wording. Narrows the spec if part of the change is already done. Adds missing-infrastructure ACs when eval sets or fixtures are absent.
Coder Every file in affected_components plus one neighbor of each. Naming, typing, error handling, imports, logging, config conventions. Matches the local convention exactly — not general best practices. Extends a nearby existing file instead of creating a parallel one. Uses the same fixture style as the tests around it.
Grader The diff plus the original files it touches Judges the diff against the actual repo conventions, not idealized ones. Fails scope creep — files changed that weren't in affected_components.
LLM Prompt Engineer Prompt files, existing eval sets, downstream parsers Preserves output schemas that downstream code depends on. Refuses prompt shape changes without a proposed migration for parsers.

The PAUSE contract

When a mode discovers something that changes the plan, it will stop and surface a PAUSE: block instead of forging ahead. You'll see it look like this in the chat:

PAUSE: partial-implementation-detected

While reading `workers/enrichment_worker.py`, I found that
`preferred_topics` is already extracted (line 87) and written to
OpenSearch (line 142). AC1, AC3 appear satisfied by existing code.

Only AC2 (prompt wording for last-30-days scope) and AC5 (eval delta)
appear to need work.

Question: should I narrow the plan to just AC2 + AC5, or is the
existing implementation known-broken and I should replace it?

Six situations trigger a PAUSE:

  • Partial implementation detected — some ACs are already satisfied by existing code.
  • Scope expansion needed — the change requires touching a component not in affected_components.
  • Missing infrastructure — no eval set, no migration harness, no fixture for the shape you need.
  • Convention conflict — the local codebase pattern contradicts the spec's implied shape.
  • Path/structure mismatch — the spec expects a module structure that doesn't exist.
  • Breaking change unearthed — a schema or field deletion that will affect other components.
Your job on PAUSE. Read the finding. Answer the specific question. Then either say "adapt and continue" (with your instruction on how) or "revise the spec first — going back to Spec Architect". Log the pause + your answer in the trace log — that's the audit for why the plan changed.

Feedback loop: what the Coder tells you when it stops

When the Coder finishes normally, its stop message is instructed to include three sections beyond the AC-by-AC summary:

  • Conventions matched — a one-liner naming the local patterns it followed (e.g. "matched the async-context pattern from workers/existing_worker.py").
  • Deviations from the Spec — anything it did differently and why (e.g. "used list[Topic] not list[str] — matches existing enriched fields; suggest updating AC1").
  • Discovered gaps — anything the Grader or the human should verify that couldn't be verified from the diff alone (e.g. "eval run needed against evals/preferred_topics.jsonl").

This feedback is what carries adaptive learnings into the Grader step and the PR body. Do not skip reading these — they often surface things that would otherwise slip through review.

Why this matters more for your specific system. The recommendation backend has hidden coupling: the enrichment prompt's output schema is consumed by the enrichment worker's write path, which is consumed by the OpenSearch mapping, which is consumed by the /recommend API's read path. A change in one spot can silently break three others. The PAUSE contract is what catches this — trust it.

10Tips, gotchas & anti-patterns

Fresh chat between Coder and Grader. Don't reuse the Coder's chat for the Grader. The Grader will be primed by the Coder's reasoning and rubber-stamp it. Open a new chat.
Use different models for Coder and Grader. Cross-model verification catches more. If the Coder ran on Sonnet, run the Grader on Opus or GPT-5.
The trace log is the audit. In three weeks when someone asks "why did we add preferred_topics?", the trace log is the only source of truth. Don't skip it — even for small tasks.
Don't skip the spec review. The habit of pausing at Step 7.4 is what catches bad ideas. Every time you skip it because "the spec looks fine", you're one step closer to a rollback.
Prompt changes need eval numbers. If the Coder edits any file under prompts/, do NOT ship without running the offline eval suite. The LLM Prompt Engineer mode reminds you — but the discipline is on you.
Copilot can't run headless. This whole workflow assumes a human at the keyboard. If you want scheduled / event-driven / batch execution, you need the runtime kit (dev-graph-starter) and programmatic API access.

Common anti-patterns

Anti-patternWhat it costs you
Using Ask mode instead of Spec Architect for spec productionYou get prose, not JSON. No ACs. Grader has nothing to check against.
Using Coder mode without an approved specYou're back to prompt engineering. All the discipline benefits evaporate.
Letting Coder loop past 20 tool calls without checking inCost creeps and edits sprawl. Pause and steer if it's off track.
Grader passes on eval-less prompt changeThe Grader mode says to fail this — trust it. Don't override.
Skipping the trace logYou lose the audit trail. Next month's you will hate current-you.

11Troubleshooting

The modes don't appear in the mode picker

  1. Confirm files exist: ls .github/chatmodes/*.chatmode.md
  2. Reload the window: Cmd+Shift+P → Developer: Reload Window
  3. Check the setting chat.modeFilesLocations — add ".github/chatmodes" if missing
  4. Verify frontmatter — the file must start with --- and include description:
  5. Check the Copilot extension version — very old versions don't support custom modes

The prompts don't appear when I type /

  1. Enable chat.promptFiles in settings (may default to off)
  2. Add ".github/prompts" to chat.promptFilesLocations
  3. Confirm each file has --- frontmatter with description:
  4. Reload the window

Copilot doesn't seem to know the repo architecture

  1. Confirm .github/copilot-instructions.md exists at the repo root's .github/
  2. Check the setting github.copilot.chat.codeGeneration.useInstructionFiles is true
  3. Ask directly: "What are your instructions?" — Copilot should mention the recommendation backend

The Coder mode won't edit files

  1. Confirm you're in Coder mode (check the mode picker)
  2. Confirm the mode's frontmatter includes editFiles in tools:
  3. Try invoking with /coder-input — the prompt file may set additional flags
  4. Some Copilot versions require Agent mode to be explicitly enabled in settings

My model of choice isn't in the picker

Model availability depends on your Copilot subscription tier and your org's admin settings. Contact your Copilot admin — models like Claude Opus and GPT-5 may need to be enabled at the org level.

Everything works but it feels slow

That's not a bug. Manual graph execution is slower than a single prompt. The discipline is the point — you're trading speed for auditability, testable specs, and independent verification. If you find yourself skipping steps, ask whether the task actually warrants the workflow (small tweaks may not).
