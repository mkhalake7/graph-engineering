01The System Being Built

Before designing the dev graph, we need a clear picture of the runtime system it produces. There are two distinct paths — a write-path pipeline that builds the enriched user profile, and a read-path API that serves recommendations. Getting these two paths right is the whole point of the backend.

  • Upstream Glue job — batch aggregation of readership + subscription data. Produces a base user profile snapshot to S3.
  • S3: base user profile — the handoff surface between the Glue job and your backend.
  • Document team's OpenSearch index — documents with tags and Limeglass embeddings, owned by another team.
  • Your backend — enrichment worker — reads the base profile from S3, fetches recent-read doc details from the docs index, runs LLM enrichment, writes the result to a second OpenSearch index.
  • OpenSearch: enriched user profile index — a distinct index (separate from the docs index) that your API reads at request time. Pre-computed so the request path stays fast.
  • Your backend — /recommend API — fetches the enriched profile + anchor doc + candidates, calls the ML library, reranks with an LLM, returns the response.
  • ML team's library — the recommendation scoring algorithm (black-box from your team's perspective).
  • LLM (Claude / equivalent) — used inside your service for user profile enrichment and for reranking.

Why the two-path split matters for the dev graph. The write path is batch-tolerant, LLM-heavy, and correctness-sensitive (bad enrichment poisons every future recommendation). The read path is latency-sensitive, request-scoped, and consistency-sensitive (a stale profile is better than a slow response). Dev tasks will almost always target one path or the other — the graph should route accordingly.

Your team owns everything in the middle: the enrichment worker, both LLM prompts, the OpenSearch enriched-profile mapping, and the recommend API. The dev graph below is designed to build, extend, and maintain exactly this surface.

02Why a Dev-Workflow Graph

You are already using prompt engineering (crafting good instructions) and loop engineering (Claude Code / Codex-style autonomous coding runs). Those work well for individual tasks. They start to break down when:

  • A feature touches multiple concerns at once — API + data pipeline + LLM prompt + OpenSearch mapping + tests.
  • You need a specialist for LLM prompt design that differs from the specialist for OpenSearch queries.
  • Work should run in parallel — a coder edits the API while another writes tests while another updates the OpenSearch mapping.
  • You need explicit human checkpoints — spec approval before code, PR review before merge, prompt approval before it hits prod.
  • You need traceability — which agent made which change, why, and what verified it.
Reframe. Loop engineering asks: "how does one agent finish one task?" Graph engineering asks: "how does an organization of specialized agents build and maintain a whole service?" Your team becomes the graph designer, not the operator of every loop.

Two things to notice:

  1. The graph has an Org shape (fixed nodes with stable roles) and a Work shape (which workers actually get called depends on the Planner's decomposition of the current task).
  2. Every cycle is bounded and explicit. No infinite retries. Failing branches route back to a specific node with feedback.

04Shared State Schema

State is the object that flows along every edge. Keeping it typed is what separates a graph from a pile of prompts.

from typing import TypedDict, Literal, Optional
from pydantic import BaseModel

class Spec(BaseModel):
    summary: str
    acceptance_criteria: list[str]
    affected_components: list[Literal[
        "glue_job",               # upstream batch, S3 output
        "enrichment_worker",      # S3 → LLM → OpenSearch (write path)
        "recommend_api",          # /recommend endpoint (read path)
        "enrichment_prompt",      # LLM prompt for user profile enrichment
        "reranker_prompt",        # LLM prompt for reranker
        "user_profile_index",     # OpenSearch mapping for enriched profiles
        "opensearch_query",       # kNN / filter queries
    ]]
    risk: Literal["low", "medium", "high"]

class Artifact(BaseModel):
    path: str
    kind: Literal["code", "prompt", "test", "mapping", "migration"]
    author_node: str
    diff: str

class DevState(TypedDict):
    # inputs
    task_id: str
    task_text: str
    trigger: Literal["ticket", "slack", "cron"]

    # produced by early nodes
    repo_context: Optional[dict]      # file list, symbols, patterns
    spec: Optional[Spec]
    spec_approved: bool

    # planning
    work_graph: Optional[dict]        # which workers to run and in what order

    # workers produce these
    artifacts: list[Artifact]

    # verification
    test_results: Optional[dict]
    prompt_eval_results: Optional[dict]
    grader_verdict: Optional[Literal["pass", "fail"]]
    grader_feedback: Optional[str]

    # control
    retry_count: dict[str, int]      # per-node retry budget
    human_approvals: list[str]

    # output
    pr_url: Optional[str]
    trace: list[dict]              # every node's inputs/outputs, for audit
Why typed state matters. The moment state becomes a free-form dict, every node has to guess what fields exist. Typed state turns node boundaries into contracts. Refactoring the graph is a mechanical exercise instead of an archaeology dig.

05Node Catalog

Each node is a pure function state → state (or state → partial state). Model choice per node matters: use the strong model where judgment is required, the cheap model where mechanical work is needed.

Intake / Router
Sonnet 4.6 Linear · Slack

Normalizes the trigger into a canonical task. Rejects obvious junk. Classifies task type (feature / bug / maintenance / experiment).

Repo Context Explorer
Haiku 4.5 grep · read · index

Read-only. Finds relevant files, symbols, existing patterns. Produces a compact repo_context. Prevents downstream nodes from re-scanning.

Spec Architect
Opus 4.7

Turns the fuzzy task + repo context into a concrete spec: summary, acceptance criteria, affected components, risk level. This is where judgment lives.

Human Checkpoint: Spec
Engineer

Interrupt. Engineer reviews the spec in a UI (or Slack thread). Approves, edits, or rejects. Nothing gets coded before this passes.

Planner
Opus 4.7

Emits the work graph for this task — which workers to invoke, in what order, which can run in parallel. Adapts topology to affected components.

API Coder
Sonnet 4.6

Writes/edits FastAPI/Flask endpoints and service layer. Owns the /recommend path, request validation, error handling, response shape.

Glue Job Coder
Sonnet 4.6

Owns the upstream AWS Glue job that reads readership + subscription data and writes the base user profile to S3. PySpark / Glue DynamicFrame changes and the S3 output schema live here.

Enrichment Worker Coder
Sonnet 4.6

Owns the backend enrichment path: read base profile from S3, fetch recent-read docs from OpenSearch, invoke the LLM enrichment prompt, write enriched profile to the user-profile OpenSearch index. Triggering logic (event / schedule / lazy) lives here.

LLM Prompt Engineer
Opus 4.7

Specialist for the two LLM-bearing components: user profile enrichment (interests/topics from read history) and reranker. Owns prompt files, few-shot examples, output schemas, guardrails.

OpenSearch Coder
Sonnet 4.6

Owns index mappings, kNN queries, tag filters, embedding fields. Coordinates with the document team's index conventions.

Schema / Migration Coder
Sonnet 4.6

Any DB migration, index reindex plan, or breaking schema change. Runs only when the spec flags schema as affected.

Test Author
Sonnet 4.6

Writes unit + integration tests against the spec's acceptance criteria. Uses fixtures for OpenSearch and the ML library.

Prompt Eval Runner
Haiku 4.5 eval suite

Runs when the LLM Prompt Engineer changed a prompt. Executes the offline eval set (labeled examples) and compares to the prior baseline.

Integration Runner
pytest · lint · mypy

Deterministic. Runs the full test suite, linter, type check, and any component-specific validators. No LLM involved.

Grader
Opus 4.7

LLM verifier. Reads the spec, the diff, and test results. Judges: does this diff actually satisfy each acceptance criterion? Returns pass/fail with feedback.

Human Checkpoint: PR
Reviewer

Interrupt. Reviewer sees the diff, the trace, the grader's report, and prompt-eval deltas. Approve, request changes, or reject.

PR Publisher
git · gh

Creates the branch, commits per-node artifacts with authorship attribution, opens the PR with a body that summarizes the trace.

Where humans must be in the loop

Non-negotiable checkpoints for a recommendation system. These are places where a fully autonomous graph will eventually cause an outage or a bad user experience. Keep the human interrupt.
  • Spec approval — before any code is written for anything user-facing.
  • Prompt changes to prod — the LLM prompt for user-profile enrichment or reranker shapes what every user sees. Never merge without eyes.
  • OpenSearch mapping changes — irreversible at scale. Require human sign-off.
  • PR review — even if the grader passes, a human reviews the merged diff.

Bounded cycles

Every retry edge carries a budget. If the API Coder fails the grader twice, the graph does not loop forever — it escalates. This is the single most important discipline that graph engineering enforces that prompt/loop engineering does not.

07Worked Example: Building User-Profile Enrichment

Concrete task: "Add a new interest-extraction field preferred_topics to the enriched user profile, populated by an LLM prompt over the last 30 days of readership, and store it in the OpenSearch user-profile index."

  1. Intake              ─▶ classifies as: feature,
                              affects [enrichment_prompt, enrichment_worker, user_profile_index]
                              (Glue job untouched — base profile already carries read history)

  2. Repo Explorer       ─▶ finds: prompts/enrichment.md
                                   workers/enrichment_worker.py
                                   opensearch/mappings/user_profile.json
                                   evals/enrichment_eval_set.jsonl
                                   tests/test_enrichment_worker.py

  3. Spec Architect      ─▶ produces spec:
                              AC1: preferred_topics is list[str], max 20 items
                              AC2: enrichment uses last 30d of reads from base profile (S3)
                              AC3: user_profile OpenSearch mapping updated with keyword field
                              AC4: existing enriched profile fields unchanged
                              AC5: eval suite shows ≥ 0.75 precision on labeled set
                              AC6: backfill plan for existing enriched profiles
                              risk: medium (prompt change reaches all users' next enrichment)

  4. HUMAN: Spec         ─▶ engineer edits AC5 to require ≥ 0.80 precision → approves

  5. Planner             ─▶ work graph:
                              parallel: [LLM Prompt Engineer,
                                         OpenSearch Coder,
                                         Enrichment Worker Coder]
                              then:     [Test Author, Prompt Eval Runner]
                              then:     Integration Runner → Grader

  6. Parallel workers:
       LLM Prompt Engineer      ─▶ updates prompts/enrichment.md
                                    (adds preferred_topics section, few-shot examples,
                                     tightens JSON schema)
       OpenSearch Coder         ─▶ adds preferred_topics field to user_profile mapping,
                                    writes reindex-in-place plan for AC6 backfill
       Enrichment Worker Coder  ─▶ extends S3-read → LLM-enrich → OpenSearch-write path
                                    to carry preferred_topics through end to end

  7. Test Author           ─▶ adds tests for AC1–AC4 (fixture-based)

  8. Prompt Eval Runner    ─▶ runs 200-example eval set. Precision = 0.72 → REGRESSION

  9. Route: Prompt Eval → LLM Prompt Engineer (with delta report)
        LLM Prompt Engineer tweaks prompt (adds "prefer specific over general" rule,
        adjusts few-shot examples), reruns → 0.83

 10. Integration Runner    ─▶ all tests pass, mypy clean, lint clean

 11. Grader (LLM)          ─▶ reads diff + spec + eval numbers → PASS with note:
                              "consider adding index reindex procedure to PR body"

 12. HUMAN: PR             ─▶ reviewer approves; PR merged

 13. Trace written back to Linear ticket with node-by-node summary

Notice what the graph gave you that a single Claude Code loop would not:

  • The prompt regression was caught by an evaluator node, not by the coding agent noticing something felt off.
  • Three components were built in parallel instead of sequentially.
  • The spec was a hard gate — the engineer changed AC5 before a single line was written.
  • Every artifact carries an authoring node, so the PR body can attribute changes.

08Implementation with LangGraph + Claude Agent SDK

Concrete stack:

  • LangGraph — the orchestration layer. Nodes, edges, state, checkpoints, interrupts.
  • Claude Agent SDK (or Claude Code as a subprocess) — the actual coding agent inside worker nodes. Each worker gets its own filesystem sandbox / worktree.
  • Postgres or SQLite checkpointer — durable state so a graph run survives restarts and human interrupts across days.
  • Your existing CI (pytest, mypy, lint) — called directly from the Integration Runner node.
  • An eval harness for the LLM prompts (labeled examples + a scorer). Owned by your team, invoked by the Prompt Eval Runner.

Skeleton

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.types import interrupt

# --- Node functions (each returns a partial state update) ---

def intake(state: DevState) -> dict:
    return {"task_text": normalize(state["task_text"])}

def repo_explorer(state: DevState) -> dict:
    ctx = run_claude_readonly(state["task_text"], tools=["grep", "read"])
    return {"repo_context": ctx}

def spec_architect(state: DevState) -> dict:
    spec = claude_opus.produce_spec(state["task_text"], state["repo_context"])
    return {"spec": spec}

def human_spec_gate(state: DevState) -> dict:
    approval = interrupt({"kind": "spec_review", "spec": state["spec"]})
    return {"spec": approval["spec"], "spec_approved": approval["ok"]}

def llm_prompt_engineer(state: DevState) -> dict:
    artifact = claude_opus.edit_prompt_file(state["spec"], state["repo_context"])
    return {"artifacts": state["artifacts"] + [artifact]}

def prompt_eval_runner(state: DevState) -> dict:
    result = run_eval_suite(prompt_paths_in(state["artifacts"]))
    return {"prompt_eval_results": result}

# ... other worker nodes similarly ...

# --- Routing ---

def route_after_planner(state: DevState) -> list[str]:
    components = state["spec"].affected_components
    workers = []
    if "glue_job"            in components: workers.append("glue_job_coder")
    if "enrichment_worker"   in components: workers.append("enrichment_worker_coder")
    if "recommend_api"       in components: workers.append("api_coder")
    if "enrichment_prompt"   in components: workers.append("llm_prompt_engineer")
    if "reranker_prompt"     in components: workers.append("llm_prompt_engineer")
    if "user_profile_index"  in components: workers.append("opensearch_coder")
    if "opensearch_query"    in components: workers.append("opensearch_coder")
    return list(set(workers))   # dedupe; LangGraph fans out in parallel

def route_after_grader(state: DevState) -> str:
    if state["grader_verdict"] == "pass":
        return "human_pr_gate"
    if state["retry_count"].get("grader", 0) >= 2:
        return "escalate_to_human"
    return pick_failing_specialist(state)

# --- Wire the graph ---

g = StateGraph(DevState)
for name, fn in NODES.items():
    g.add_node(name, fn)

g.add_edge(START, "intake")
g.add_edge("intake", "repo_explorer")
g.add_edge("repo_explorer", "spec_architect")
g.add_edge("spec_architect", "human_spec_gate")
g.add_conditional_edges("human_spec_gate",
    lambda s: "planner" if s["spec_approved"] else "spec_architect")
g.add_conditional_edges("planner", route_after_planner)

# all workers fan-in to test_author + prompt_eval_runner
for w in WORKER_NODES:
    g.add_edge(w, "test_author")
g.add_edge("llm_prompt_engineer", "prompt_eval_runner")

g.add_edge("test_author", "integration_runner")
g.add_edge("prompt_eval_runner", "integration_runner")
g.add_edge("integration_runner", "grader")
g.add_conditional_edges("grader", route_after_grader)
g.add_edge("human_pr_gate", "pr_publisher")
g.add_edge("pr_publisher", END)

app = g.compile(checkpointer=PostgresSaver.from_conn_string(DSN))
Worktrees per worker. Give every coder node its own git worktree so parallel edits do not collide. Merge back at the fan-in point (Test Author sees a combined view). This is the same pattern the graph itself embodies at the code level.

09Phased Rollout

Do not build the whole graph on day one. Ship it in three phases.

Phase 1 — Linear pipeline (2–3 weeks)

  • Nodes: Intake → Repo Explorer → Spec Architect → Human Gate → single Coder → Integration Runner → Human PR Gate → PR Publisher.
  • No parallelism yet. No grader. No prompt eval. No specialist workers.
  • Goal: prove the checkpointer works, humans get sensible interrupts, PRs are clean.

Phase 2 — Specialization + fan-out (3–4 weeks)

  • Add Planner, split Coder into API / Data / OpenSearch / LLM Prompt specialists.
  • Add Test Author as a distinct node.
  • Add parallel fan-out from Planner. Introduce per-worker worktrees.

Phase 3 — Verification + self-improvement (ongoing)

  • Add Grader and Prompt Eval Runner.
  • Add bounded-retry cycles.
  • Start collecting traces to a store; use them to refine prompts (hill-climbing loop from Level 4 of loop engineering).

10Anti-Patterns to Avoid

Anti-patternWhy it hurts
One giant "coder" node that does everything Collapses back to loop engineering. You lose specialization, parallelism, and per-domain retry.
Free-form dict as state Nodes drift, contracts erode, refactors get scary. Use Pydantic or TypedDict from day one.
No retry budget Graphs cycle infinitely on tricky bugs and burn tokens. Every retry edge needs a numeric bound.
Grader written by the same author as the coder Grader becomes a rubber stamp. Keep the grader's prompt and evaluation criteria owned by a different engineer.
Human checkpoints on every node You lose the leverage of automation. Checkpoints belong at high-risk gates only (spec, prod-touching prompt, schema, merge).
Prompt changes without an eval suite Every prompt change is a silent product change. For the reranker especially, no eval means no signal.
Building the graph before you have working loops You cannot organize agents that do not yet work individually. Get each node's loop reliable in isolation first.
No trace / no observability When something goes wrong at 2am, you will need to know which node did what with which state. Log every node transition.
Closing thought. The dev graph is not a replacement for your team's engineering judgment — it is an amplifier for it. The graph shape is a codified statement of how your team wants to build software. Change the graph as your team's practices evolve.
