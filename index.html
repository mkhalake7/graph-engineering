Prompt vs Loop vs Graph Engineering

A three-layer stack for building modern AI systems — and a deep dive into the layer that ties them together.

01TL;DR

Prompt engineering (2022–) optimizes a single LLM call. You control what the model receives; it replies once.

Loop engineering (June 2026–) designs the system that autonomously prompts an agent. The unit of work becomes a full run, not a single turn.

Graph engineering (Mid-2026–) coordinates multiple agents as an explicit state machine — nodes, edges, and shared state — turning a fleet of loops into a programmable organization.

They are additive. Every graph node contains a loop. Every loop turn uses a prompt. The question is which layer is your current bottleneck.

02The Stack

Each layer sits on top of the ones below. You cannot skip a layer — you can only choose how much sophistication to invest at each.

03Prompt Engineering

2022 → Present

What it is

The craft of writing inputs that get the best output from a single LLM call. You control what the model receives; the model replies once; you evaluate and refine.

Core techniques

TechniqueWhat it does
Role promptingAssign a persona ("You are a senior security auditor…")
Chain-of-thoughtAsk the model to reason step-by-step before answering
Self-consistencyGenerate multiple reasoning paths, pick the most consistent
Few-shot examplesShow 1–3 worked examples inline
Meta-promptingAbstract, structural templates that minimize example-induced bias
Output format controlExplicitly specify JSON, markdown, or schema
PrefillingStart the model's reply to steer format and tone

What changed in 2026

Modern frontier models (Claude Sonnet/Opus 4.x) need less scaffolding. XML tags, heavy role-play, elaborate few-shot chains — all matter less now. The discipline has split cleanly in two:

  • Casual prompting — anyone can do it; models read intent well.
  • Production context engineering — a genuine engineering skill: curating what goes into the context window, not decorating a single instruction.

Hard limits

  • Optimizes one turn at a time
  • Humans still drive every step
  • Says nothing about what happens next, what counts as "done," or how to contain cost
  • Cannot handle workflows that span minutes or hours

04Loop Engineering

June 2026 → Present

What it is

Designing systems that autonomously prompt AI agents instead of you prompting them by hand. The unit of work shifts from a single LLM call to a full autonomous run.

"Stop prompting your agents. Start designing the loops that prompt them."

The four levels

Level 1 — The Agent Loop (execution)

Give the model context → let it call tools → observe results → loop until done. Transforms an LLM from a passive question-answerer into an active agent.

Level 2 — The Verification Loop (quality)

Wraps the agent loop with a grader that evaluates output against criteria. If it fails, feed back and retry. Graders can be deterministic (CI tests, schema validation) or agentic (an LLM scoring the result).

Level 3 — The Event-Driven Loop (integration)

Connects agents to continuous systems via triggers — cron, webhooks, channel messages. The agent becomes infrastructure: always-on, reactive.

Level 4 — The Hill-Climbing Loop (self-improvement)

Analyzes production traces, detects patterns, refines prompts, tools, and graders automatically. Human judgment compounds each cycle.

Five components of any loop

  1. Trigger — schedule, event, webhook, or another agent
  2. Goal — a verifiable end state (not just "do a good job")
  3. Actions — the tool set available to the agent
  4. Verification — how the system confirms completion
  5. Memory — context persistence across iterations

What loop engineering solves

Prompt engineering couldn't answer: Which turn comes next? What counts as done? Who approves before an irreversible action? How does spend stay capped? Loop engineering addresses all of these by making the orchestration layer explicit.

Real-world anchors: Claude Code, OpenAI Codex, and IBM Bob all run on agentic loops. Andrew Ng frames three loops in practice: an agentic coding loop, a developer feedback loop, and an external user feedback loop.

05Graph Engineering — Deep Dive

Mid-2026 → Present

What it is

Graph engineering treats the entire agent workflow as an explicit state machine. Where loop engineering built a single agent that iterates, graph engineering builds a network of specialized agents that coordinate.

"Loops made agent behavior programmable. Graphs make agent organizations programmable."
Core primitives.
Nodes — individual agents or functions (LLM calls, tool invocations, data transforms)
Edges — control-flow transitions or routing logic (fixed or conditional)
State — a shared typed object that flows across the graph (often a Pydantic model or TypedDict)
Checkpoints — snapshots enabling durable, resumable workflows

Why loops weren't enough

A loop hides complexity inside conditional logic. As agents took on longer, more parallel, more auditable work, that opacity became a liability. Graphs make the topology declarative: control flow, dependencies, failure paths, and human checkpoints are all visible.

CapabilityLoopGraph
Parallel fan-out / fan-inHardNative
Conditional routingAd hocDeclarative
Human-in-the-loop interruptsBolted onFirst-class
Durable state across sessionsDifficultBuilt-in checkpoints

The two graphs in a production system

Org Graph (structural)

Stable, long-lived agents with named roles, zone ownership, persistent memory, and fixed dependencies. Think of it as an org chart where every position runs its own autonomous loop — Security, Data, API, Frontend, etc.

Work Graph (dynamic)

Ephemeral task nodes with adaptive edges that split, merge, and reorder as complexity is discovered. Tasks appear and disappear per request. Regenerated for each incoming job.

Three core patterns

Advisor–Orchestrator

A strategic planner (Opus-class) routes work to specialized workers (Sonnet-class). Achieves high quality at a fraction of the cost of running the top model for every step. This is the workhorse pattern.

Zone Defense

Specialized agents each own a domain (Security, Data, API, Frontend) and maintain persistent context within their zone. Prevents cross-zone context pollution and makes each agent a genuine expert instead of a generalist forced to hold everything at once.

Multi-LLM Deliberation

Fixed topology with dynamic content: multiple agent personas reason independently, then pass through anti-groupthink gates before reaching a verdict. Common in high-stakes decisions — investment memos, security reviews, code architecture calls.

LangGraph — the reference implementation

LangGraph embodies these principles using a message-passing model inspired by Google's Pregel. Nodes complete work and update state; edges route to the next node. It supports parallel execution, conditional routing, human-in-the-loop interrupts, explicit cycles, and state persistence across sessions.

A minimal graph looks like this:

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END

# 1. Shared state — the object flowing along every edge
class AgentState(TypedDict):
    request: str
    plan: list[str]
    draft: str
    verdict: Literal["pass", "fail"]

# 2. Nodes — each is a pure function of state → state
def planner(state: AgentState) -> dict:
    return {"plan": llm_plan(state["request"])}

def writer(state: AgentState) -> dict:
    return {"draft": llm_write(state["plan"])}

def grader(state: AgentState) -> dict:
    return {"verdict": llm_grade(state["draft"])}

# 3. Conditional routing — the essence of graph engineering
def route(state: AgentState) -> str:
    return "done" if state["verdict"] == "pass" else "retry"

# 4. Wire the graph
graph = StateGraph(AgentState)
graph.add_node("planner", planner)
graph.add_node("writer", writer)
graph.add_node("grader", grader)

graph.add_edge(START, "planner")
graph.add_edge("planner", "writer")
graph.add_edge("writer", "grader")
graph.add_conditional_edges("grader", route, {
    "done": END,
    "retry": "writer",   # cycle — but explicit and bounded
})

app = graph.compile(checkpointer=sqlite_checkpointer)  # durable

Notice what became explicit: the retry loop, the failure route, the state schema. In a hand-rolled loop, all of that is buried in conditionals. In a graph, it is the API.

Empirical results

Anthropic's own multi-agent research showed graph-organized agents outperformed a single-agent baseline by 90.2% on complex research tasks — but with significantly higher token consumption. Graphs optimize for specialization and concurrency, not raw efficiency.

The tradeoff. Graphs cost more tokens per task. You pay for parallel exploration, specialized workers, and verifier passes. The right question is not "is graph engineering cheaper?" but "is the outcome worth the token spend?" — which for complex, high-value, or high-stakes work, it usually is.

The hard part

"Loops are forgiving. Graphs force you to admit how much of the workflow you haven't modeled yet."

Graphs require upfront architectural clarity: who owns what, what depends on what, what happens when a branch fails. That rigor is the cost. The payoff is a system you can reason about, audit, extend, and hand to another engineer.

When to reach for graph engineering

  • Tasks that naturally decompose into parallel subtasks
  • Workflows where specialized agents outperform a generalist
  • Systems requiring human approval gates at specific points
  • Regulated or audited domains that need traceable execution
  • Long-running work that must survive restarts (durable state)
  • Multi-model routing — expensive model plans, cheap model executes

When not to

  • A single agent solves the problem in one loop
  • You do not yet know the shape of the workflow — prototype in a loop first, extract a graph later
  • Token budget is the binding constraint
  • The task is genuinely serial with no branching

07Decision Framework

Diagnose the bottleneck before adding complexity:

SymptomLayer to fix
Output quality is poorPrompt
Tasks won't finish autonomouslyLoop
Can't scale, coordinate, or audit multiple agentsGraph
Retries are chaotic and un-observableLoop (verification) or Graph
Need human approval at a specific stepGraph (interrupts)
Need to run cheap model for most steps, expensive for oneGraph (routing)
Workflow survives crashes and resumesGraph (checkpoints)
Rule of thumb. Start at the lowest layer that solves your problem. Do not build a graph when a loop will do; do not build a loop when a prompt will do. But do not fight a graph problem with better prompts either — that is the most common failure mode of 2026.
